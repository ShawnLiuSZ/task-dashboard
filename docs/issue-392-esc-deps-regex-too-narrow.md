## 实测缺口：#344 的依赖数组正则只匹配一种写法

守卫原文：

```ts
expect(raw, `${name} 不得把 onClose/onCancel 放进 Esc effect 依赖`).not.toMatch(
  /\}, \[on(Close|Cancel)\]\)/,
);
```

**只匹配依赖数组「恰好等于」`[onClose]` 的形态。**

而 #344 要防的是「**不稳定的回调依赖导致 Esc 层整体重排**」这**一类**问题（面板压过自己的子层 ⇒ 一次 Esc 跳过取消直接关面板），不是「恰好等于 `[onClose]`」这一个写法。

### 注入验证

在 `SyncLogsPanel` 注入一个带 Esc 监听 + 不稳定依赖的 effect：

| 依赖数组形态 | 旧正则 | 修复后 |
|---|---|---|
| `}, [onClose]);` | exit=1 捕获 | exit=1 捕获 |
| `}, [onClose, t]);` | **exit=0 漏网** | exit=1 捕获 |
| `}, [t, onClose]);` | — | exit=1 捕获 |
| `}, [onClose, onClose]);` | — | exit=1 捕获 |
| `}, [onCancel]);` | — | exit=1 捕获 |
| `}, [deps]);`（不含回调） | — | exit=0 **不误报** ✅ |
| `}, []);`（稳定，正确写法） | — | exit=0 **不误报** ✅ |

`ConfirmDialog` 的 `[onCancel, x]` 同样被捕获。

## 后果

`[onClose, t]` 是**完全自然**的写法 —— 任何人在 deps 里多留一个变量就绕过守卫，而 #344 的失效机制**照样发生**。

这是 #390 那类盲区的轻量版：**守卫覆盖了「问题的一个实例」，而非「问题的一类」**。

## 设计 / 方案

```diff
- /\}, \[on(Close|Cancel)\]\)/
+ /\},\s*\[[^\]]*\bon(Close|Cancel)\b[^\]]*\]\)/
```

匹配**任何含 `onClose` / `onCancel` 的依赖数组**，允许中间有其他依赖。

### 关键取舍

`[deps]` 与 `[]` **不误报**：

- `[]` 是正确写法（稳定依赖），本就不该匹配
- `[deps]` 字面上不含回调。若用 `onClose` 是否被**间接**引入来判定，会误伤大量正常代码

**遗留局限（如实记录）**：间接依赖（`useCallback` / 自定义 hook 内部把回调吃进去）**当前无法被字面量正则发现**。要覆盖它需要解析依赖来源，成本远高于收益，故标注为局限而非强上。

## 过程中连续两次测量手段出错（第八、九次）

### ⑧ 用 grep 解析输出判结果

```sh
npx vitest run ... | grep -oE "Tests .*" | head -1
```

抓到的是 `Tests 1 ⎯⎯⎯`（失败输出行，不是汇总行），被判成「存活」—— 而实际是**捕获**。差点把 5 个形态全判反。

### ⑨ 自写判定脚本用错误字符串判全绿

```sh
grep -q "No tests failed"
```

该字符串并非 vitest 的输出，**恢复态（本来就该全绿）就误报失败** —— 等于整张表的结论全部作废。

### 最终方案：只用退出码

```sh
(cd app && npx vitest run src/panel-wiring.test.ts >/dev/null 2>&1); echo $?
```

`0` = 全绿，`1` = 有失败。**唯一无歧义的信号**，一次跑完全部形态。

> **这是本轮系列最该记住的一条：判结果只用退出码，不要解析输出文本。**

前七次测量错误（注入未生效 / 变异方向反 / 期望值手算 / 过滤条件漏用例 / grep 漏 `errors=` / vitest 变换缓存）都是「采信了某个信号」；本次两条则证明**信号本身的选取**也会错。
