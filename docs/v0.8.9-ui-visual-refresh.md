## 一、背景与根因

### 1.1 触发

用户诉求：「优化一下界面的视觉风格，生产优化文档」。落到工程上，需要先回答一个问题：**当前界面的视觉问题到底是「审美不够好」，还是「视觉系统本身是坏的」？**

勘察结论是后者居多。以下六类缺陷全部**可复现、可量化**，且其中四类在 node 环境的 vitest 里**一个都测不出来** —— 这决定了本次必须同步补断言，而不只是改 CSS。

### 1.2 量化基线（重构前）

| 指标 | 重构前 | 重构后 |
|---|---|---|
| 非令牌处硬编码色值 | **235** | **0** |
| 圆角取值种类 | **12** | **4**（全令牌） |
| `:focus-visible` 出现次数 | **0** | **8** |
| `color-mix()` 实际声明 | **3**（全部失效） | **0** |
| 规则块总数 | 504 | 485（删 26 条僵尸规则） |
| 深色块覆盖的令牌数 | 27 | **78** |
| `z-index` 字面量 | 8 | **0**（全部走 `--z-*`） |
| 死令牌（定义但引用数 0） | — | **0**（`--accent-active` / `--accent-focus` 已接线；`--focus-halo` 已废止） |
| 行数 / 字节 | 3685 / 87954 | 3962 / 106885 |

硬编码 px 共 705 处、rem 仅 20 处 —— 但 **20 处 rem 全部是 `font-size`**，零处用于间距或尺寸。这个事实是 §3.8 决策的关键前提。

### 1.3 六类根因

#### ① 根字号从未接线 ⇒ 用户改字号偏好**完全无效**

`app/src/fontPrefs.ts` 把 `--font-size-base` 写到 `document.documentElement` 的内联样式，运行时确实生效。但 `styles.css` **从没有给 `html` 设过 `font-size`** ⇒ 根字号恒为浏览器默认 16px ⇒ `0.8125rem` 恒为 13px ⇒ 字号档位（12/13/14/16/18）对全部 20 处 rem 元素**零影响**。

更讽刺的是 `app/src/styles.test.ts` 那条断言的注释原文写着「主层级字号用 rem（**随 `--font-size-base` 缩放**）」—— **这句注释是假的**，它断言的 `0.8125rem` 字面量存在，但那个 rem 根本不缩放。

⇒ WCAG 1.4.4「调整文本大小时不应丢失内容或功能」实质失效。

#### ② 深色模式覆盖块几乎为空 ⇒ 124 处写死色值在深色下失配

`[data-theme='dark']` 块原本只覆盖 27 个变量，而全表有 339 处 hex。实测的暗色破损：

| 元素 | 浅色取值 | 深色下的实测 | WCAG |
|---|---|---|---|
| `--status-0..19`（20 组） | 纯 hex | 深色块**一个都没覆盖** ⇒ 沿用浅色值，2.09–4.61:1 | 1.4.11 ❌（13/20 达标） |
| `.repo-0..19` 标签 | 写死浅底深字 | 深底上是一块**亮斑** | ❌ |
| 四态列头 | `#dbe9fc` / `#d8eee5` / `#d2ebdf` | 仍是**亮 pastel 块** | ❌ |
| `.column-processed .column-title` | `#157a58` on `#d8eee5` | **1.43:1** | 1.4.3 ❌❌ |
| `.dot-processed` | `#30b386` on `#d8eee5` | **2.18:1** | 1.4.11 ❌ |
| `.dot-todo` | `#8e8e93` on `#f0f1f3` | **2.89:1** | 1.4.11 ❌ |

#### ③ `color-mix()` 在生产构建里**整条失效**（3 处）

`app/vite.config.ts` 的 `build.target = chrome105 / safari13`，而 `color-mix()` 需 **Chrome 111 / Safari 16.2**、`oklab()`/`oklch()` 需 **Chrome 111 / Safari 15.4** ⇒ Vite 的 postcss **不做该函数降级** ⇒ 声明原样送出浏览器 ⇒ **整条声明被丢弃**（不是降级成别的值）。

三处受害点与实际后果：

| 位置 | 声明 | 运行时真实表现 |
|---|---|---|
| `.live-badge` | `background: color-mix(…accent 12%…)` | **无底色**，只剩文字 |
| `.session-card.selected` | `background: color-mix(…accent 8%…)` | **选中态只剩边框、没有底色** |
| `.note-dot` | `box-shadow: 0 0 0 1.5px color-mix(…)` | **无色环** |

⚠️ 而 `.session-card.selected` 上原先的断言是 `expect(d).toMatch(/background/)` —— **文本匹配**，只检查源码里有没有 "background" 字样 ⇒ 断言通过，运行时整条失效。**这是典型的假阳性断言**（详见 §6.2）。

#### ④ 焦点环：0 处 `:focus-visible` + 2 处 `outline: none`

全表 `:focus-visible` 出现 **0** 次；`.note-textarea:focus` 与 `.note-editor-textarea:focus` 各写了 `outline: none`（后者还配了一个透明度仅 0.1 的 `box-shadow`，远低于 1.4.11 的 3:1）。

⇒ 键盘用户**看不出焦点在哪**（WCAG 2.4.7 失效）。且 `TaskCard` 根元素已有 `role="button"` + `tabIndex={0}` + Enter/Space 绑定 ⇒ 卡片**可聚焦但无焦点指示**。

#### ⑤ 圆角 12 种、硬编码 px 705 处

圆角分布：`4px`×20 / `6px`×13 / `8px`×10 / `5px`×5 / `10px`×5 / `50%`×4 / `7px`×3 / `12px`×2 / `0`×2 / `999px`×1 / `20px`×1 / `14px`×1 ⇒ 同类元素圆角不一，视觉不统一。

#### ⑥ 书写顺序陷阱：`.repo-N` 被 `.gh-status` 整体覆盖

`TaskCard.tsx` 的状态徽章同时带三类：`gh-status repo repo-${hash}`。而 CSS 里 `.repo-N`（20 条）排在 `.gh-status` **之前** ⇒ 同特异性下**后者胜出** ⇒ `.gh-status` 的 `background` / `color` / `font-size` 全部覆盖掉 `.repo-N`。

⇒ `TaskCard.tsx` 注释里那句「同状态保持一致颜色」的承诺**从未生效过**，徽章一直是中性灰 10px。详见 §5.3。

## 二、设计目标与硬约束

### 2.1 目标

1. **视觉系统自洽**：全站颜色 / 圆角 / 阴影 / 间距从令牌派生，明暗两套**结构同构**（同一个变量名在两个块里都有定义）。
2. **暗色模式不是「反色」**：深色块覆盖全部有语义色，而不是沿用浅色值。
3. **可访问性达标**：正文 ≥ 4.5:1、图形/状态指示 ≥ 3:1、焦点可见且不被裁剪。
4. **可回归**：视觉约束落到断言上，删掉实现必须让测试红。

### 2.2 五条硬约束（任何实现不得违反）

| # | 约束 | 依据 |
|---|---|---|
| H1 | **禁用 `color-mix()` / `oklab()` / `oklch()`**，混色一律落成预计算 hex | `vite.config.ts` 的 `build.target = chrome105 / safari13` |
| H2 | **既有变量名一个都不能改**（`--bg` `--surface` `--text` `--accent` `--status-0..19` `--session-card-border-1..4` 等） | 运行时动态引用 + 既有断言 |
| H3 | **既有 `:root` 变量必须保留**：缺一个即触发 `styles.test.ts` 的「`var(--x)` 必须已定义」断言 | `styles.test.ts` |
| H4 | **字号：徽章 / meta 的 10–12px 保持 px**；13/14px 主层级不得再以 px 出现 | `styles.test.ts` 既有断言 |
| H5 | **零新依赖 / 零 DB 改动 / 不动 `theme.ts` 与 `fontPrefs.ts`** | 仓库硬约束 |

## 三、设计方案

### 3.1 令牌层总览

`:root`（浅色 + 主题无关）共 134 个声明，`[data-theme='dark']`（深色覆盖）共 78 个。**同名重定义**是本方案的核心手法 —— 深色块只重定义值，规则本身不需要任何 `[data-theme='dark'] .xxx` 选择器：

```css
:root              { --repo-0-bg: #f3e7e8; }
[data-theme='dark'] { --repo-0-bg: #4f3c46; }
```
```css
/* 规则只需一行，两主题自动切换 */
.repo-0 { background: var(--repo-0-bg); color: var(--status-0-text); }
```

### 3.2 中性色阶梯（冷中性灰，4 档）

深浅两套**结构同构**：`bg < surface-2 < surface-raised < surface`。

| 变量 | 浅色 | 深色 | 用途 |
|---|---|---|---|
| `--bg` | `#eef0f4` | `#15171c` | 页面底 |
| `--surface` | `#ffffff` | `#23272f` | 卡片面 |
| `--surface-2` | `#f6f7fa` | `#1c1f26` | 徽章 / 输入框底（列容器底） |
| `--surface-raised` | `#ffffff` | `#2b303a` | 浮起层 |
| `--text` | `#15181e` | `#e7eaef` | 正文（17.78:1 / 12.41:1） |
| `--text-2` | `#565d6b` | `#a6aebc` | 次级（6.62:1 / 6.70:1） |
| `--text-3` | `#666e7b` | `#9099a8` | 三级（5.15:1 / 5.21:1） |

原深色主题是**紫调**（`#1a1a2e` / `#25253d` / `#2d2d4a`），本轮改为冷中性灰以与浅色同族。原 `--text-3` 为 `#6b6b70`（4.84:1），收紧到 `#666e7b`（5.15:1）。

### 3.3 accent 与焦点环

新增 `--accent-active` / `--accent-focus` / `--accent-soft` / `--accent-soft-strong`，把「主色 / 交互态 / 焦点 / 淡底」四类职责分开。

**焦点环三段式**（顺序不可调换）：

```css
:focus                          { outline: 2px solid var(--accent); outline-offset: 2px; }  /* 旧引擎兜底 */
:focus:not(:focus-visible)      { outline: none; }        /* 鼠标点击不留环 */
:focus-visible                  { outline: 2px solid var(--accent); outline-offset: 2px; }
```

- 主环用**不透明** `--accent`：半透明环在浅底上会被稀释到 3:1 以下。
- 用 `outline` 而非 `box-shadow`：`box-shadow` 会被祖先 `overflow` 裁掉，且不跟随 `border-radius`。
- **偏移分档**：`.card:focus-visible { outline-offset: -2px }` —— 卡片住在 `.column-body`（`overflow-y: auto` 滚动容器）里，外扩 4px 的环会被裁掉；向内偏移保证 WCAG 2.4.11「焦点不被遮挡」。⚠️ **不得**对 `.btn.primary` / `.chip.on` 用向内偏移 —— 它们底色就是 `--accent`，向内偏移会让环与底色同色 ⇒ **完全隐形**。

### 3.4 status 色系：两个令牌、两种职责（关键设计）

`--status-0..19` 在 OKLCH 空间求解（色相覆盖全色轮、亮度带约束、两两色差有下限），并**拆成两个令牌**：

| 令牌 | 用途 | 对比度门槛 | 实测 |
|---|---|---|---|
| `--status-N` | 色块 / 圆点 / 徽章**底色** | ≥ 3:1（1.4.11） | 浅 3.03–6.70:1、深 4.36–11.47:1，**20/20 达标** |
| `--status-N-text` | **文字**色 | ≥ 4.5:1（1.4.3） | 浅 6.00–6.16:1、深 6.00–6.12:1，**20/20 达标** |

⚠️ **误用 `--status-N` 当文字色会让 11/20 组跌破 4.5:1（最低 3.03）** —— 这正是必须拆两个令牌的原因。这条口径在三阶段之间曾被两位成员算成「冲突」，最终由主理人独立复算澄清。

### 3.5 仓库标签双主题

20 组 `--repo-N-bg`（浅色淡彩底 / 深色暗彩底）+ 20 组 `--status-N-text`（字色）。深色块内**同名重定义**，规则只需一行。

### 3.6 四态列头与圆点

四态色相最终为 **todo 中性灰 / doing 蓝 243° / processed 琥珀 63° / done 翠绿 153°**。

- 原方案 processed 与 done **都是绿系**（`#30b386` / `#0b6b4f`）⇒ 相邻两列头难以区分；琥珀把四态拉成四段可辨色相带。
- 列头**始终有文字冗余**（列名），满足 WCAG 1.4.1「不能只靠颜色表达状态」。
- 圆点对比度必须按「**圆点 × 其所在列头底色**」算，不是 × surface。实测：浅 3.40–4.28:1、深 4.76–6.34:1。

### 3.7 间距 / 圆角 / 阴影 / z-index

- **间距**：`--space-1..6`，**固定 px**（4/8/12/16/24），不随字号缩放（理由见 §3.8）。
- **圆角**：12 种 → 4 档（`--radius-sm/md/lg/full`），映射表见 §4.3。
- **阴影**：`--elevation-0..3` 四档；`--shadow` / `--shadow-strong` 保留定义（既有引用方不动），新增的规则改引 `--elevation-*`。
- **z-index**：`--z-base/sidebar/sticky/toolbar/detail/modal-mask/modal/note-viewer`，把原先散落的裸数字收进语义层。

### 3.8 字号阶梯与根字号接线 —— 三阶段决策演进

这是本次**唯一有实质分歧**的设计点，记录全过程：

| 方案 | 做法 | 判定 |
|---|---|---|
| **路线 B** | `html { font-size: var(--font-size-base) }` + 整张 rem 阶梯重算 | ❌ 13px 基准下根字号变 13px ⇒ `0.8125rem` 变 10.4px ⇒ **全站视觉缩小 20%** |
| **路线 A** | 新增 `--fs-*` 档位令牌，根字号不动 | ❌ 需改 20 处 `font-size`，而 `styles.test.ts` 正是断言 **`0.8125rem` / `0.875rem` 字面量存在** ⇒ 这些 rem 变成**死锚点**，断言退化为假阳性；且与 rem 阶梯形成两套并行字号体系 |
| **路线 C** ✅ | `html { font-size: calc(var(--font-size-base) * 1.23076923) }` | ✅ **只改 1 行**，20 处 `font-size` 一行不动，锚点仍是活锚点 |

系数 `1.23076923 = 16 / 13`：

| `--font-size-base` | 根字号 | `0.8125rem` 实得 | `0.875rem` 实得 | 视觉 |
|---|---|---|---|---|
| 12px | 14.77px | 12.0px | 12.9px | 等比 |
| **13px（默认）** | **16px** | **13px** | **14px** | **与现状逐像素一致** |
| 14px | 17.23px | 14.0px | 15.1px | 等比 |
| 16px | 19.69px | 16.0px | 17.2px | 等比 |
| 18px | 22.15px | 18.0px | 19.4px | 等比 |

**为什么间距不跟着缩放**：现有 20 处 rem **全部是 `font-size`**，零处用于间距/尺寸 ⇒ 根字号接线**只影响字号、零布局副作用**。而新引入的 `--space-*` 一律用 px：看板列宽固定 320px，间距若随字号放大，18px 档下卡片可用宽从 300px 掉到 276px ⇒ **字号越大信息密度越低**，与放大字号的目的相反（WCAG 1.4.4）。

⇒ 立场：**「字号偏好 = 只放大字，不放大盒」**。

#### 6.5.4 链接 chip 的 WCAG 1.4.3 缺陷与「形状通道」悬停（Phase 3 末批）

**缺陷本体**：`.cmt-link`（卡片底部「新评论」链接胶囊）与 `.pr-link`（PR 链接胶囊）共用一条规则 `color: var(--accent); background: var(--accent-soft)`，而 `.cmt-link` 字号 **10px**（正常文本 ⇒ 阈值 4.5:1，无大字号豁免）⇒ 主理人**独立复算**：浅 **4.04:1** / 深 **4.13:1** ❌❌ 两主题均不达标。

> ⚠️ **根因不在色值，在「令牌职责」**：`--accent` 是**色块色**（按 WCAG 1.4.11 选的 ≥3:1 图形色），被当成**文字色**（需 ≥4.5:1）用 ⇒ 一个色值承担不了两档门槛。这与 `--status-N` 必须配 `--status-N-text` 是同一条道理。

**修法（主理人拍板：方案 B「专用文字色 + 专用底」）**：
- `.cmt-link` 改用 `--info` 字 + `--info-bg` 底 ⇒ 实测 **4.97 / 5.66** ✅；
- 与 `.pr-link` 的 `--teal-text` + `--teal-bg`（5.60 / 7.77 ✅）**同构** —— 同一类 chip 走同一套「语义色 + 配对语义底」范式；
- **零新令牌**：`--info` / `--info-bg` 已在 `:root` 与深色块各自定义；
- 代价（已知并接受）：深色主题底色由 `#2c3b50` → `#16243a`（略深）；`--info` 保留蓝色链接联想，不像改成 `--text` 那样把链接「洗白」成普通文字。

**悬停反馈走「形状通道」（下划线），不改底色** —— 这是本批唯一需要独立论证的一条：

| 候选 | 实测 | 判定 |
|---|---|---|
| 底色改 `--accent-soft-strong` | 深色 `--info` on `--accent-soft-strong` = **3.40:1** | ❌ 破 AA（4.5） |
| 底色改 `--surface-2` | 胶囊褪成中性 | ❌ 读作「弱化」而非「强调」 |
| **下划线（形状通道）** | 与底色**无关** ⇒ 对比度恒为 **4.97 / 5.66** | ✅ **采纳** |

⇒ `.cmt-link:hover` / `.pr-link:hover` 统一为 `text-decoration: underline`。**这同时修掉了两个缺陷**：
1. **悬停零反馈** —— 旧规则「常态底 = hover 底（都是 `--accent-soft`）」⇒ 鼠标悬停**没有任何视觉变化**；
2. **`.pr-link:hover` 色相家族漂移** —— 旧写法 hover 时底色从 teal 家族换成 accent（蓝）家族 ⇒ 读作「换了个东西」；改用下划线后常态/悬停底色恒为 `--teal-bg`。

**同批补的第二处 Safari 降级缺口（`.toggle` 三段式）**：

`.toggle input` 是 `opacity:0; width:0; height:0` 的**零尺寸元素** ⇒ 焦点环必须画在兄弟节点 `.slider` 上（Phase 2 §4.3）。但原实现只写 `.toggle input:focus-visible + .slider` ⇒ ⚠️ **`:focus-visible` 需 Safari 15.4**，而 Tauri 2 的 WKWebView 在 macOS 12 落在 **15.0–15.3** ⇒ 未知伪类让**整条选择器失效**（不是降级成别的值）⇒ 该规则在旧引擎上**直接消失** ⇒ 而 input 是零尺寸元素 ⇒ **toggle 焦点环彻底消失**（WCAG 2.4.7 失败）。

修法为完整三段式（与全局 `:focus` 三段式同构）：

```css
.toggle input:focus + .slider              { outline: 2px solid var(--accent); outline-offset: 2px; }  /* ① 旧引擎兜底 */
.toggle input:focus:not(:focus-visible) + .slider { outline: none; }                            /* ② 鼠标点击不留环 */
.toggle input:focus-visible + .slider     { outline: 2px solid var(--accent); outline-offset: 2px; }  /* ③ 键盘导航 */
```

⚠️ **② 不可省**：全局的 `:focus:not(:focus-visible) { outline: none }` 只作用于 **input 自身**，**管不到兄弟节点 `.slider`** ⇒ 少了 ②，鼠标点击 toggle 时环会一直留着。
⚠️ 特异性：② (0,4,1) > ① (0,3,1) = ③ (0,3,1) ⇒ 顺序 ①→②→③ 时键盘态由 ③ 兜底、鼠标态由 ② 清掉，且 ② 在键盘态下不匹配（键盘焦点满足 `:focus-visible`）⇒ 互不打架。

#### 6.5.5 「同色换底不成立」—— 新增背景色令牌的全局不变量

> **本节是给后续维护者的硬约束，任何人新增一个背景色令牌都必须走这张表。**

**一条颜色通过 AA 只对它被选定的那个底色成立** —— 把同一色值挪到另一个底上，**必须重新逐格复算**。本轮实测的三次「同色换底」全部翻车：

| 换底情形 | 原判定 | 换底后实测 | 结论 |
|---|---|---|---|
| `--accent` 作文字色 on `--accent-soft` | —— | 浅 4.04 / 深 4.13 | ❌ 原判定就错（色块色当文字色） |
| `--teal-text` on `--teal-bg` | 5.60 / 7.77 ✅ | 换成 `--accent-soft-strong` 后 5.23 / 6.14 ✅ | ⚠️ 数值达标但**语义不一致**（换底必须复算，不能推定） |
| `--info` on `--info-bg` | 4.97 / 5.66 ✅ | 换成 `--accent-soft-strong` 后深色 **3.40** | ❌ 破 AA |

⇒ **新增任何背景色令牌时，必须同时给出下列 4 列字色矩阵并标 ❌**（表样见 §6.4）：

| 承载底 | `--text` | `--text-2` | `--text-3` | `--accent`（作**文字**） |
|---|---|---|---|---|
| **（新令牌，浅 / 深各一行）** | 必填 | 必填 | 必填 | 必填 |

**判定口诀（三条）**：
1. **默认且唯一通则是 `--text`** —— 强调底上写字，先假定 `--text`；
2. **`--accent` 是填充色，不是文字色** —— 换一个底就要重新复算，不得以「它在别处达标」推定；
3. **语义色走「语义色 + 配对语义底」范式** —— 换成强调底只是偶然达标。

#### 6.5.6 本批的断言补强与反向验证

| 断言 | 守什么 | 反向验证 |

| `.cmt-link:hover` / `.pr-link:hover` **不得出现 `background:`** | 悬停走形状通道（防改底色破 AA） | 改回 `background: var(--accent-soft-strong)` ⇒ 变红 ✅ |
| `.cmt-link:hover` / `.pr-link:hover` 必须有 `text-decoration: underline` | 悬停有反馈 | —— |
| `.pr-link` 常态底必须是 `--teal-bg` | 防色相家族漂移 | —— |

**反向验证的操作纪律**：注入缺陷前**必须先备份文件**、注入后**必须确认测试变红**、随后**还原并确认全绿** —— 三步缺一不可。此前发生过一次「脚本在第二处锚点 assert 失败 ⇒ 异常抛出 ⇒ `open(p,'w')` 从未执行 ⇒ 第一处改动也丢失」，若当时用**假设值**而非**文件实际内容**做验证，就会得出「已修复」的错误结论。

#### 6.5.7 静态扫描式判据的三类陷阱（本轮踩过，写给后来者）

本轮大量断言是对 `styles.css` 源码做正则扫描（vitest 在 node 环境运行、没有布局引擎，纯 CSS 缺陷只能这样守）。但**扫描式判据本身也会骗人**，实测踩过三类：

| # | 陷阱 | 表现 | 正确写法 |
|---|---|---|---|
| 1 | **注释污染** | 注释里写「原先用 `overflow: hidden`」⇒ 断言「不得出现 `overflow: hidden`」被注释命中，或反向被注释里的正确写法喂成假阳性 | 先把 `styles.css` 的 `/* … */` 全部剥掉再扫；⚠️ **正向扫描同样会被污染** |
| 2 | **属性名后缀误命中** | 用 `color\s*:\s*var\(--accent\)` 扫「`--accent` 作文字色」会命中 **`border-color:` / `background-color:`**（`color` 是它们的后缀）⇒ 一次扫出 17 处「疑似缺陷」，严格化后真实只有 **5 处** | 加左边界：`(?:^\|[;{\s])color\s*:` |
| 3 | **启发式推断令牌类别** | 「以 `-text` / `-bg` 结尾的算颜色类令牌」这类靠名字猜的判据，遇到 `--text-3`（颜色类）与 `--font-size-base`（非颜色类）会双向误判 | **颜色类令牌必须显式列出白名单**，不从命名推断 |

⇒ 还有一条更根本的：**所有跨文档引用的数值，以 `styles.css` 工作树的实际值为唯一事实源**。本轮的 `phase3-impl.md` 曾有一张 `--status-N-text` 终值表，重写时被删除，只剩作废值；其中深色那套把**色块色本身**当字色，对真实落点底 `--repo-N-bg` 只有 **4.45–4.46:1** —— 差 0.04 刚好卡在 AA 4.5 之下，是最容易被顺手抄进汇编文档的一类数。同理，`--sem-*` 八组语义色板从未落地，**本期只承认 Phase 1 第 10 章的五族**（`--success` / `--warning` / `--danger` / `--error` / `--info`），最终文档不出现第二套语义色体系。

⚠️ **文档不写行号**：并发批次里 `styles.css` 在 40 分钟内被改了 9 次 ⇒ 任何 `styles.css:1234` 都会立刻过期。本交付文档一律用**选择器名 + 令牌名**定位（例：`.note-composer:focus-within` 的 `border-width`）。

## 七、风险与回滚

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 深色主题整体换色，用户需重新适应 | 语义色映射未变（绿仍是绿、红仍是红），只有 processed 改琥珀；提供主题切换即时生效 |

| R4 | 根字号接线后 18px 档布局密度变化 | 间距固定 px ⇒ 盒子尺寸恒定；已按「内容宽不变 + 文字变大」验收 |

| # | 事项 | 原因 |

| L1 | `role="list"` 与 `role="button"` 语义冲突（`Board.tsx` 的 `.column-body` 是 `role="list"`，直接子元素却是 `role="button"` 的卡片） | 属 ARIA 语义层，需改 DOM 而非样式；影响读屏播报，需单独排期 |

| L3 | 看板上无侧栏入口（`Sidebar.tsx` 的 `NavKey` 含 `'board'` 但渲染分支只有 notes/sessions） | 信息架构问题，非视觉层 |
| L4 | base=18 时 `.card-title` 仍 12px，层级压缩 33% | 修它需把 `.card-title` 改 rem，与「徽章/meta 保持固定 px」的分层原则冲突；需要先定「标题 vs 正文」在 18px 档的期望比例 |
| L5 | 仓库色与列色共用 20 槽色系（仓库芯片带文字标签，可区分） | 现状本就同色系（改造前是 Tailwind 色阶）；若将来「仓库色」被赋予独立语义，必须拆独立色板 |
| L6 | 响应式仅 5 个 `@media`（1100px×2 / 1400px / 900px / prefers-reduced-motion） | 缺 768px / 1920px 断点；属布局层，本轮未动 |
| L7 | 状态徽章的状态语义改由文字承载；若将来要给状态上**语义色**（如 Blocked=红），需建立「状态名 → 颜色」映射表 | 本轮明确否决哈希着色（§5.3） |
| L8 | **`--space-*`（5 档）未全面接线** | 实测 `padding/margin/gap` 共 **279 条声明 / 322 个 px 值 / 17 种数值**。Phase 3 的后续拆分显示其中 **89 处全落在 scale 内**（纯机械替换、像素值不变、视觉零变化），另 **109 处含非 scale 值**（6px 31 处最常见）。⚠️ **这不构成「覆盖不了」的借口** —— 那 89 处技术上完全可做，本轮不做的原因是：本批 `styles.css` 已有 **+1143 行 diff**，再叠 89 处机械替换会把 review 面扩大而**视觉收益为零**；且「半接线」（一部分走令牌、一部分留字面量）比「明确不接线」更难维护（后来者分不清哪些是刻意例外）。⇒ 要做得**一次性做完 + 扩档**，单列一个批次 |
| L9 | **base=18px 档下 `.card-title` 仍 12px，与 `.repo`（18px）的比例 0.67** | 唯一解是让 `.card-title` 也进 rem 档，但那会抹平卡片内「标题 vs meta」的层级。是否需要 ≥0.78 的比例属 UX 口味，**未拍板** ⇒ 维持现状（L4 已记录层级压缩），等视觉评审给定期望比例再动 |
| L10 | **`.card:hover` 不加 `--elevation-1` 浮起阴影（O6 驳回）** | Phase 1 §7.2 曾提出「卡片悬停浮起」，但用真实 `styles.css` + 复刻 `.column-body` DOM 做 **Chrome 无头实测**：卡片上缘距滚动容器顶 **0px**，而 `--elevation-1` 有 8px 模糊半径（向下外扩约 10px、向上约 8px）⇒ `.column-body { overflow-y: auto }` 会**裁掉上缘/横向阴影** ⇒ 浮起变成糊边。这正是 Phase 2 §4.2.1「滚动容器内卡片只保留 `outline` 主环、不用 box-shadow 柔光」要防的形态 ⇒ 维持现有 `border-color` 反馈。**这是本期唯一被驳回的「新增视觉」** |

**开放项裁定（Phase 3 交主理人拍板的 O2/O3/O6/O7）**：

| 项 | 裁定 | 依据 |
|---|---|---|
| **O2** 表格 6px 间距 | **保留为「紧凑表格」显式例外** | 6px 不在 5 档 scale（4/8/12/16/24）内 ⇒ 归并等于改视觉（表格被撑松 31 处），超出「视觉优化不重排内容」的边界 |
| **O3** `.sync-logs-modal` 宽度 | **落地**：`max-width: 90vw` → `calc(100% - 48px)` | 同一批弹窗不该有两套边距口径（48px vs 10vw），窄窗口下实际留白还不一样；宽度基准仍是 720px（宽表格需要空间） |
| **O6** `.card:hover` 加阴影 | **驳回**，见 L10 | Chrome 无头实测会被滚动容器裁掉 |
| **O7** `.gh-status` 的 `max-width` + ellipsis | **落地：删除三条声明** | `.card-top .gh-status { flex: 0 0 auto }` 让元素按内容宽度参与 flex、不收缩 ⇒ **省略号永不触发**。状态徽章文本天然很短，截断反而损失信息；留着「看着能用、其实不生效」的声明会误导后来者 |
